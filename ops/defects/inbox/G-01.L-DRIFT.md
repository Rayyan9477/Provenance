# G-01 · lens `L-DRIFT` — contract drift between the specs and the task plan

Source: the T1.2 and T1.3 builds (2026-08-18). Both builders were told to report
discrepancies rather than resolve them silently, and these are the ones where the
**spec-as-written and the spec-as-remembered disagree**, which is what `L-DRIFT` is for.

Two findings below (`F-L-DRIFT-1`, `F-L-DRIFT-6`) have already been corrected in
`70_TASK_PLAN.md`; they are still submitted, because §6 makes suppressing a
finding because it is already fixed the triager's decision, not the reporter's.

## F-L-DRIFT-1
summary:  70_TASK_PLAN T1.2 states the trigger lifecycle as ARMED -> SCHEDULED -> WOKEN -> (FIRED|DISARMED|EXPIRED|ERROR), a machine over enum members that do not exist
repro:    python -c "from provenance_domain.enums import TriggerState; print(sorted(m.value for m in TriggerState))"
observed: ['ARMED', 'DISARMED', 'EXPIRED', 'FIRED'] — zero overlap with {SCHEDULED, WOKEN, ERROR}
expected: the lifecycle expressed as (state, result) -> state per 16_TRIGGER_DSL §9.10, with TriggerState unchanged
file:     docs/EXECUTION/70_TASK_PLAN.md

Built from that bullet alone a builder adds three members to a canon-frozen enum. It
surfaces at Phase 10, where wakeups are persisted — far from where it was introduced.
Corrected in place; submitted so the correction is on the record.

## F-L-DRIFT-2
summary:  legal_transition is declared `-> bool` by 11_CONTRACTS §4 and `-> TransitionVerdict` by the task plan and 20_TDD_STRATEGY §5.1
repro:    grep -n "legal_transition" docs/specs/11_CONTRACTS.md docs/EXECUTION/70_TASK_PLAN.md docs/quality/20_TDD_STRATEGY.md
observed: §4 declares -> bool and §20.1 writes `assert not legal_transition(...)`; the task plan requires a verdict object carrying the rejecting guard and reason code
expected: one declared return type
file:     docs/specs/11_CONTRACTS.md

Reconciled in code by a verdict whose `__bool__` is its legality, so both call styles are
literally true. The documents still disagree and a later gate asserting either shape in
isolation will read as a contract violation.

## F-L-DRIFT-3
summary:  the exception is named IllegalTransition by the canon register and IllegalTransitionError by 11_CONTRACTS §4 and its own §20.1 tests
repro:    grep -rn "IllegalTransition" docs/
observed: both spellings, in documents of different authority
expected: one name
file:     docs/specs/11_CONTRACTS.md

Shipped as one class with both names bound, so a second exception type cannot come into
existence. A closed reason-code set is only as closed as the exception that carries it.

## F-L-DRIFT-4
summary:  the T1.2 acceptance clause calls legal_transition('RESOLVED','REOPENED', reason_code=...) with the machine elided, and RESOLVED is a member of two machines
repro:    python -c "from provenance_domain.enums import CaseStatus, ConflictStatus; print('RESOLVED' in {m.value for m in CaseStatus}, 'RESOLVED' in {m.value for m in ConflictStatus})"
observed: True True
expected: a signature that cannot silently answer about the wrong machine
file:     docs/EXECUTION/70_TASK_PLAN.md

Deliberately not guessed. A machine-defaulting two-argument form would answer confidently
about CaseStatus when the caller meant ConflictStatus. Needs a spec amendment, not an
implementation choice.

## F-L-DRIFT-5
summary:  11_CONTRACTS §5 defines no money.py; the task plan creates one and assigns Money's whole acceptance list to it
repro:    grep -n "^### 5\.\|money\.py" docs/specs/11_CONTRACTS.md
observed: §5's three subsections are invariants.py, authority.py, derivations.py; §5.1 models money as a bare Decimal beside a sibling currency string, and the only Money CLASS in the pack is the pydantic one in provenance_contracts.base (§6)
expected: either a §5 subsection describing the domain-side Money, or the acceptance clauses rewritten against the §5 shape
file:     docs/specs/11_CONTRACTS.md

There are now two money types in the system with no document relating them. That is the
condition under which a float creeps into one of them.

## F-L-DRIFT-6
summary:  "reject negative committed amounts" in the T1.3 constructor clause contradicts §5.1 and §4.3, which require a negative outstanding to be representable
repro:    grep -n "Over-fulfilment\|do not silently clamp" docs/specs/11_CONTRACTS.md docs/specs/12_KERNEL_ALGORITHMS.md
observed: §5.1 "Over-fulfilment yields a negative outstanding"; §4.3 makes that visibility the point of "do not silently clamp"
expected: the ban scoped to the committed argument, not to the type
file:     docs/EXECUTION/70_TASK_PLAN.md

A Money that refuses negatives cannot hold the over-fulfilment anomaly the kernel is
required to surface. Resolved by scoping the ban to the argument; the clause still reads
as a type-level ban and the next builder will implement it that way.

## F-L-DRIFT-8
summary:  11_CONTRACTS §5.2's own code block advertises AUTHORITY_BANDS in __all__, a name it never defines
repro:    grep -n "AUTHORITY_BANDS\|AUTHORITY_SCORES" docs/specs/11_CONTRACTS.md
observed: __all__ lists AUTHORITY_BANDS; the module defines AUTHORITY_SCORES
expected: __all__ matching the module
file:     docs/specs/11_CONTRACTS.md

Transcribed verbatim, this is an ImportError at first use. The same block's chained
`.get(...).get(...)` also fails mypy --strict, so the spec's code does not typecheck under
the settings the spec itself mandates.

## F-L-DRIFT-9
summary:  11_CONTRACTS §5 contains no authority RANKING, although both the task plan and §5's own title assign one to it
repro:    grep -n "predicate_family\|authority_for\|rank" docs/specs/11_CONTRACTS.md
observed: §5.2 ships predicate_family and authority_for only; the ordering that decides an incumbent is 12_KERNEL_ALGORITHMS §3.3 decide(), in a Phase 4 module
expected: the task plan pointing at §3.3 for the ranking half
file:     docs/EXECUTION/70_TASK_PLAN.md

The risk is a reader treating an authority ranking as a disposition. Gates H1–H6
short-circuit before the ranking is consulted, and the hero conflict resolves on H5
(monetary exposure >= 100.00), not on the authority margin — so a ranking that "wins"
does not mean the conflict resolves that way.
