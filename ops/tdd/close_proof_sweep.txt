WHY NO `python -m tools.close_proof <id>` OUTPUT APPEARS BELOW
--------------------------------------------------------------
Phase 0 was authored before this repository had commit discipline. Every Phase 0
non-test fix landed in 62e3f1c27cb60997d54720f86f17a0957320196a, which is also
the commit that CREATED the file it fixed, so `git checkout 62e3f1c^ -- <path>`
has no blob to restore: the parent is c2a0c05, a docs-only commit. The mechanical
counterfactual cannot run and would print a tooling error rather than a verdict.

The counterfactual itself still can, and did. Section 7.4's question is whether
the named test distinguishes the fixed system from the broken one; the mechanical
revert is one way to ask it, not the question. Each proof neuters the mechanism
by hand in an isolated worktree at HEAD, runs the named test there, and requires
a non-zero exit - using the neutering that the test's own docstring names, so a
reader can repeat it. Every Close-proof field in the ledger says which of the two
shapes produced it. No record claims a mechanical close-proof that was not run.

WHAT THIS SWEEP DID NOT DO
--------------------------
It did not re-fix anything. Where a fix looks wrong or incomplete it is reported
to the Integrator as a finding, because re-fixing during a verification sweep
destroys the independence the sweep exists to provide.

It did not touch D-00-004 (its disposition is a Phase-15 disclosure obligation),
D-00-039 (still open and still real), or anything under packages/, docs/,
ops/gates/, the Makefile, .gitleaks.toml, or the two defect tools.
