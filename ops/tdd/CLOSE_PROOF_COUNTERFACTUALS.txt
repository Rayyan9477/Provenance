Authority: docs/EXECUTION/72_DEFECT_PROTOCOL.md section 7.4.

  > A defect may be closed only by a test that would have caught it.

WHY THIS FILE EXISTS INSTEAD OF `python -m tools.close_proof <id>` OUTPUT
------------------------------------------------------------------------
tools/close_proof.py implements section 7.4 mechanically: it checks out the fix
commit into a scratch worktree, restores the PARENT's blobs for the non-test
paths, runs the record's pytest node id, and requires a non-zero exit.

Phase 0 was authored before this repository had commit discipline. Every Phase 0
non-test fix landed in 62e3f1c27cb60997d54720f86f17a0957320196a, which is also
the commit that CREATED each of those files. `git checkout 62e3f1c^ -- <path>`
therefore has no blob to restore: the parent is c2a0c05, a docs-only commit. The
mechanical counterfactual cannot run, and running it would print a tooling error
rather than a verdict.

The COUNTERFACTUAL ITSELF still can. Section 7.4's question is "does the named
test distinguish the fixed system from the broken one", and the mechanical
revert is one way to ask it, not the question. So each proof below neuters the
fixed mechanism BY HAND in an isolated git worktree at HEAD, runs the named test
there, and requires a non-zero exit. The neutering for each record is the one
its own test docstring names under "Neuter to prove it", so the proof is
repeatable by a reader rather than trusted.

Every run is one of these two shapes and neither is weaker than the other in the
respect that matters: the test is run against a tree in which the mechanism is
absent, and it must go red.

METHOD, EXACTLY
---------------
  1. git worktree add --detach <scratch>/wt HEAD
  2. apply one neutering to one file in that worktree
  3. python -m pytest -q <the record's Verifying assertion>
  4. require a non-zero exit
  5. git checkout -- <file>, then assert `git status --porcelain <file>` is empty

Step 5 is asserted in code, not remembered: the driver raises if any file is not
restored byte-for-byte. Nothing here touched the working tree of the repository.

Three records are proved TWICE because their fix has two independent halves and
either alone would be vacuous:

  D-00-011   the exit_code check, and the S1..S10 id family      (11, 11b)
  D-00-013   the sendto reach, and the credential unsetter       (13, 13b)
  D-00-023   the version comparison, and the gate-0 call site    (23, 23b)

READING A BLOCK
---------------
`close-proof <id>: test FAILED with the fix neutered (exit=N) - PASS` is the
verdict. PASS means the test went red without the mechanism, which is what
section 7.4 requires. A `FAIL` line would mean the named test passes without the
fix and therefore does not catch the defect; there are none below, and four
earlier attempts that did print FAIL were re-done with a faithful neutering
rather than recorded — a neutering that does not actually remove the mechanism
proves nothing, and neither does one that breaks the file so the test errors on
collection instead of failing an assertion (section 7.1: a RED test must fail
for the right reason).
